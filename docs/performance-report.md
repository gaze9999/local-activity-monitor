# 效能與資料上限

## 分批收集

啟動先預載有界對話目錄, 讓列表可在首輪活動整理前呈現, 此時完整更新時間及尚未取得的活動數值維持缺值. 單一 worker 依序整理 session、統計、工作樹、帳戶、診斷、歷史、MCP、Jev 與硬體資訊. 快照 API 其後使用最近完整結果, 收集取消或失敗時保留上次快照

Session 清單在來源變更時重掃, 掃描全部可取得的來源. 初次從檔頭分批讀取, 後續依位移差異讀取. 每輪共用 8 MiB 預算, 使用輪替游標處理多檔及歷史回補

完整輸入輸出、SQL、Log、Git、技能文件與檔案 metadata 透過明細 API 按需取得. 同一內容以 revision 核對後續分頁

## 畫面更新

前端更新目前頁面與已選總覽卡片. 圖表接近可視範圍後逐張繪製, 新快照及 Tab 切換取代舊排程. 圖表設定在第一次開啟齒輪時建立

WBUI 共用卡片控制器負責布局, LAM 更新可見項目並在移除容器或離開頁面時釋放. 背景更新保留已開啟明細、捲動位置及草稿

本機 SSE 直接傳送目前時間範圍的有界快照與 Log, 每個畫面一條連線, 斷線由瀏覽器重新連線. 來源以原生檔案通知觸發收集, 不執行固定間隔輪詢. 瀏覽器隱藏時關閉串流. 沒有來源變更時等待通知. CPU、記憶體與效能歷史在收集時取得樣本, 執行時間由畫面本機時鐘推算

大量 SSE 快照只保留最新待套用資料, 同一畫面影格合併渲染. 滑鼠或鍵盤焦點停留在表格時保留目前列, 離開後套用最新資料. 用戶端最多 8 條連線, 慢速寫入有逾時保護, 連線結束釋放名額與監聽執行緒

開發者工具的 EventStream 清單會保留觀察到的事件, LAM 不保存前端事件序列. SQLite 歷史依保存天數分批清理, 預設 90 天, 0 停用自動清理. 刪除過期列後資料庫空間可供後續寫入重用, 檔案大小不一定立刻縮小. Codex 來源 Log 由來源管理

## 回補與無回補比較

2026-10-09, Windows、Python 3.14.7, 隔離合成資料. 同一組 24 個 session 檔案, 每檔 321 個事件, 合計約 7.39 MiB. 各組使用全新 home, 串行執行兩次, 每次兩輪回補與四輪無新增資料更新. 停用工作樹與硬體查詢, 量測包含收集與快照投影, 未加入 profiler

| 階段 | 樣本數 | 整理耗時平均 | 程序 CPU 平均 | 每輪讀取量 | 輪末待回補檔案 |
| --- | --- | --- | --- | --- | --- |
| 回補第一輪 | 2 | 3,480.66 ms | 2,406.25 ms | 6 MiB | 5 |
| 回補第二輪 | 2 | 1,805.30 ms | 1,437.50 ms | 1.39 MiB | 0 |
| 無回補、無新增資料 | 8 | 1,029.22 ms | 958.98 ms | 0 B | 0 |

同一程式其餘流程固定, 另以修改前的 `ActivityHistory` 比較: 第一輪平均 3,909.64 ms、第二輪 1,922.67 ms、無回補 1,097.06 ms. 修改後省去重複 metadata 投影與未變更資料的重寫, 並保留每批 500 筆的過期清理, 清理未完成時繼續下一批

此組資料的回補成本高於無回補更新, 回補完成後仍有統計投影與快照成本. 正式資料的檔案數、保留事件、硬體查詢與工作樹均會影響耗時, 介面中的整理耗時、CPU 與當輪讀取量可用來辨識目前階段

## 未變更歷史資料的 CPU 比較

2026-10-09, Windows、Python 3.14.7, `v0.11.0` 提交前修正. 使用相同 24 檔、321 事件 / 檔的合成資料, 合計 7,744,416 bytes. 每組使用全新 home, 執行兩次並交替先後順序, 每次包含兩輪回補、四輪無新增資料更新及一輪追加 24 個呼叫. 停用工作樹與硬體查詢, CPU 與耗時量測不含 profiler

修正以 32 bytes 的 SHA-256 摘要比對已驗證輸入, 輸入超過 1 MiB 時也能略過未變更的歷史寫入與合併. 歷史快照保留即時時間篩選與獨立複製, 省去已驗證欄位的重複投影. 失敗寫入不更新摘要, 後續成功重試會恢復來源健康狀態

| 階段 | 每組樣本數 | 修改前 CPU 平均 | 修改後 CPU 平均 | 修改前耗時平均 | 修改後耗時平均 |
| --- | --- | --- | --- | --- | --- |
| 回補第一輪 | 2 | 3,343.75 ms | 3,843.75 ms | 4,909.11 ms | 5,631.74 ms |
| 回補第二輪 | 2 | 1,867.18 ms | 1,984.37 ms | 2,396.28 ms | 2,651.43 ms |
| 無回補、無新增資料 | 8 | 1,255.86 ms | 947.26 ms | 1,402.84 ms | 1,080.32 ms |
| 追加 24 個呼叫 | 2 | 3,343.75 ms | 3,179.69 ms | 4,663.00 ms | 4,492.99 ms |

這組資料的無新增更新平均 CPU 減少約 24.6%, 耗時減少約 23.0%. 回補兩輪較慢, 尚未證實改善, 兩次樣本不足以判定長期差異. 四個時間範圍的呼叫數、每輪讀取量、待回補數與 SQLite 保存筆數均與修改前一致, 追加資料後完整保存 3,864 筆 MCP 紀錄

此結果是合成資料的收集與快照比較, 正式來源的 CPU 變化尚未量測. 該次量測使用 SSE 版本通知

## 來源通知與 CPU 時間

2026-10-10, Windows, Python 3.12.14, 同一 Python 環境與 12 檔合成對話資料, 先完成暖機, 停用工作樹、硬體查詢與帳戶 API. 基準為 `a1cc7fe` 的固定輪詢, 比較本次來源通知實作. CPU 為整個測試區間的程序 CPU 時間, 不含前端、HTTP 傳輸與 DevTools, 每種情境量測一次, 新版 Debug 關閉

| 情境 | 舊版 10 秒輪詢 | 來源通知 | 舊版 1 秒輪詢 |
| --- | --- | --- | --- |
| 無新資料, 22 秒 | 2 輪, 78.12 ms CPU | 1 輪啟動整理, 15.62 ms CPU | 未量測 |
| 8 秒內寫入 16 次 | 1 輪, 78.12 ms CPU | 7 輪, 734.38 ms CPU | 4 輪, 218.75 ms CPU |

此資料的無新資料 CPU 減少約 80.0%, 啟動後不再固定收集. 持續寫入時, 來源通知提供較密集更新, CPU 增加, 8 秒區間約占單一 CPU 核心 9.2% 時間. 收集仍依序執行並合併未處理通知, 不建立每筆事件的工作佇列. 樣本數與資料量小, 正式來源的差異需以實際檔案數、工作樹及讀取量比較

隔離 Edge 頁面連續測試 6 批、每批 200 個約 231 KB 的快照, 共 1200 個事件合併為 6 次渲染. 暖機後 DOM 元素維持 4460 個, 回收後 JS heap 約 9.88 - 10.01 MB, 暖機後四批差異約 0.13 MB. 另以 150 筆診斷資料測試 200 個 Debug 事件, 合併為一次更新, 200 組快照與 Debug 事件也只渲染一次. 此測試檢查短時間大量事件的保留量, 長時間正式來源與慢速網路仍需依實際負載觀察

相同 8 秒、16 次寫入的 Debug 開啟樣本為 7 輪、703.12 ms CPU. 單次結果受取樣與執行差異影響, 本組未量到較高 CPU, 尚不足以判斷診斷額外成本. Debug 記錄包含程序累計 CPU, 可用相同工作階段的兩筆差異除以經過時間比較. RSS 為程序當下常駐記憶體, 峰值為程序歷來最大值, 不能用峰值增加判斷垃圾未回收

## 閒置程序 I/O 比較

2026-10-10, Windows、Python 3.12.14, 舊版為 `a1cc7fe`, 新版為工作目錄來源 SHA-256 `5eca1b6a748e` 開頭的原始碼. 兩版凍結原始碼, 每次使用新的隔離 home 與相同 12 檔合成資料, 先完成手動整理、worker 啟動整理及通知穩定, 再量測 65 秒無來源變更. 停用工作樹、硬體查詢、帳戶 API、HTTP 與 Debug, 每版執行兩次, 順序為舊 / 新、新 / 舊. 舊版使用預設 10 秒輪詢與 5 分鐘閒置門檻, 本組尚未達到門檻

讀寫量使用 [GetProcessIoCounters](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getprocessiocounters) 的程序 I/O 累計差, CPU 使用程序 CPU 時間. 量測入口先以 256 KiB 檔案核對讀寫計數均增加 262,144 bytes. 這些計數包含程序發出的 I/O, [Windows 檔案快取](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/subsystem/cache-memory-management/)會影響實際磁碟存取, SSD 實際讀寫量與快取命中率需另行量測

| 65 秒閒置指標 | 舊版 10 秒輪詢, 每次 | 新版來源通知, 每次 |
| --- | --- | --- |
| 程序讀取量 | 676,844 bytes, 約 660.98 KiB | 0 bytes |
| 讀取操作 | 215 次 | 0 次 |
| 程序寫入量 / 操作 | 0 bytes / 0 次 | 0 bytes / 0 次 |
| 其他 I/O 操作 | 10,125 次 | 0 次 |
| 完整整理 | 5 次 | 0 次 |
| session 內容讀取增量 | 0 bytes | 0 bytes |
| 程序 CPU | 281.25、343.75 ms, 平均 312.50 ms | 兩次皆 0.00 ms |

兩次讀寫計數一致, 新版沒有新增來源收集或程序 I/O. 舊版的 session 內容沒有新增讀取, 完整整理仍產生其他程序讀取與 I/O 操作. 本組寫入量兩版皆為零, 差異主要來自反覆讀取與整理. CPU 的 0.00 ms 表示此次程序 CPU 計數未增加, 量測範圍為後端收集 worker

另以 fixture 將舊版最後來源變更時間設為 301 秒前, 核對 `paused=true` 後量測 65 秒一次. 舊版停止完整整理與資料讀寫, 仍執行 6 次來源檢查、1,098 次其他 I/O 操作, 程序 CPU 為 15.62 ms. 這組檢查閒置模式, 5 分鐘門檻由 fixture 狀態提供

重現方式見[測試與建置](validation.md), 數值結果保存於本機 `.local/source-update-io-performance.json`

## 來源新增資料時的程序 I/O

使用相同凍結來源、Python、12 檔合成資料及停用項目, 每版執行兩次並交換順序. 暖機後量測 35 秒, 另一個程序在前 20 秒每秒追加一筆 Token 紀錄, 合計 3,903 bytes. 最後 15 秒等待兩版讀完, 每次核對最新 Input Token 均為 20. 產生資料程序的 I/O 與 CPU 排除於量測

| --- | --- | --- |
| 程序讀取量 | 582,927 bytes, 約 569.26 KiB | 3,650,990 bytes, 約 3.48 MiB |
| 讀取操作 | 186 次 | 1,178 次 |
| 程序寫入量 | 24,744 bytes, 約 24.16 KiB | 156,712 bytes, 約 153.04 KiB |

| session 內容讀取增量 | 3,903 bytes | 3,903 bytes |
| 程序 CPU | 359.38 ms | 1,882.81 ms |

兩版最終讀取相同來源內容, 新版在寫入期間提供更密集的更新. 此組程序讀取量約為舊版 6.26 倍、寫入量約 6.33 倍, 整理次數也增加至約 6.33 倍. 每輪寫入均為 8,248 bytes, 較高總量主要隨整理頻率增加. CPU 平均約占單一核心 1.03% 與 5.38% 時間, 執行時機及當次來源規模仍會影響每輪成本

閒置時可省去重複整理與 I/O, 持續變更時需支付更密集整理與保存的成本. 這組結果適用於本機合成後端收集, 正式來源、HTTP 與瀏覽器的長時間成本仍需依實際負載量測. 數值結果保存於本機 `.local/source-update-io-active-performance.json`

## 來源通知的整理與保存成本

2026-10-10, Windows、Python 3.12.14, 比較來源 SHA-256 `5eca1b6a748e` 與 `ef435ace7dd3` 開頭的原始碼, 兩者均使用來源通知與 SSE. 使用相同 12 檔合成資料, 先完成暖機, 每版量測兩次並交換順序. 工作樹、硬體查詢、帳戶 API、HTTP 與 Debug 關閉
